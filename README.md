## Overview

Multi-Robot Path Planning (MRPP) is the problem of finding collision-free paths for a fleet of robots, each moving from a start position to a distinct goal, while minimizing total travel time and conflicts. Classical centralized solutions do not scale well with the number of robots. This project addresses that limitation by training a **decentralized GNN-based policy** where each robot makes its own movement decision using only local observations and communication with nearby neighbors.

The model learns from expert demonstrations generated by a modified **A\* algorithm** and generalizes across different grid sizes and robot counts without retraining.

**Key characteristics:**
- Fully decentralized execution — each robot acts independently at inference time
- Communication modeled via a dynamic adjacency matrix based on field-of-view (FOV)
- Trained end-to-end with imitation learning (cross-entropy loss against A\* expert actions)
- Supports real robot deployment via IR sensor integration

## System Architecture

The pipeline consists of four learned components working in sequence:

```
Local Observation (2-channel grid)
         │
         ▼
  ┌─────────────┐
  │ CNN Encoder │  — Extracts spatial features from each robot's FOV
  └──────┬──────┘
         │
         ├── Rank Embedding (robot priority)
         │
         ▼
  ┌─────────────┐
  │     GNN     │  — Aggregates features from neighboring robots (k-hops)
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │  MLP Action │  — Outputs a probability distribution over 5 actions
  └──────┬──────┘
         │
         ▼
  Action: {Idle, Left, Forward, Right, Backward}
```

**Input channels per robot:**
- **Channel 2:** Obstacle map within the robot's local FOV
- **Channel 3:** Goal position map within the robot's local FOV

**Adjacency matrix** is computed dynamically at each timestep based on each robot's field-of-view radius, enabling communication only between robots that are within range of one another.

├── Dataset_Generator.py      # Generates training datasets using the A* expert planner

## Usage

### 1. Generate a Dataset

Use the A\* expert planner to generate training data for a given configuration:

```python
from Dataset_Generator import DatasetGenerator

generator = DatasetGenerator(
    num_robots=10,
    grid_size=(40, 40),
    num_cases=10000
)
generator.generate()
```

### 2. Train the Model

Open `Model.ipynb` or instantiate `decentralizedModel` directly:

```python
from Decentralized_Model import decentralizedModel

model = decentralizedModel(
    cases=cases,
    tensors=tensors,
    rfov=5,                        # Robot field-of-view radius
    adjacency_matrix=adj_matrix,
    num_of_robots=10,
    k_hops=2,
    num_epochs=150,
    checkpoint_path='checkpoint.pth'
)

model.train_model()
```

Training automatically saves a checkpoint after each epoch. If a checkpoint file exists, training resumes from where it left off.

### 3. Evaluate the Model

```python
# Held-out test set accuracy
test_loss, test_acc = model.test_model()

# Full simulation evaluation with conflict tracking
python Test_Model.py
```

### 4. Deploy on Physical Robots

```python
python Robot_Main_Program.py
```

Ensure the IR sensor drivers in the `IR_sensor/` directory are compiled and accessible on the target hardware before running.

## Evaluation Metrics

The following metrics are recorded during simulation-based testing across 1,000 test cases per configuration:

| Metric | Symbol | Definition |
|---|---|---|
| **Cases Reached** | CR | Number of cases where **all** robots reached their goals within the step threshold, regardless of conflicts |
| **Number of Steps** | NoS | Total steps taken to complete all successful cases |
| **Conflicts Number** | CN | Total number of node or edge conflicts across all simulations. Node conflicts are detected by counting duplicate robot positions at the same timestep |
| **Cases with Conflict** | CWC | Number of test cases that experienced at least one conflict |
| **Success Rate** | SR | Fraction of cases where all robots reached their goals within the threshold **and** with no conflicts |

## Results

The model was evaluated across varying numbers of robots and grid sizes. Each configuration was tested over **1,000 simulation cases**.

| Robots | Grid Size | CR   | NoS   | CN  | CWC | SR    |
|:------:|:---------:|:----:|:-----:|:---:|:---:|:-----:|
| 10     | 40×40     | 1000 | 48524 | 56  | 42  | 95.8% |
| 10     | 30×30     | 998  | 37850 | 133 | 94  | 90.4% |
| 10     | 20×20     | 999  | 24677 | 410 | 243 | 75.6% |
| 8      | 30×30     | 1000 | 35075 | 65  | 49  | 95.1% |
| 8      | 20×20     | 999  | 23736 | 168 | 117 | 88.2% |
| 6      | 30×30     | 1000 | 33472 | 37  | 26  | 97.4% |
| 6      | 20×20     | 999  | 22613 | 65  | 53  | 94.6% |
| 4      | 20×20     | 999  | 20893 | 14  | 10  | 98.9% |
| 4      | 10×10     | 998  | 10609 | 74  | 60  | 93.8% |
| 4      | 5×5       | 993  | 5657  | 390 | 296 | 69.7% |

**Key observations:**

- The model achieves up to **98.9% success rate** on sparse configurations (4 robots on a 20×20 grid), demonstrating strong performance in low-density environments.
- Performance degrades gracefully as robot density increases. Even in the most congested tested scenario (10 robots on a 20×20 grid), the model still reaches a **75.6% success rate** — a challenging benchmark for decentralized planners.
- Conflict frequency is tightly correlated with grid density, as expected. Larger grids give robots more space to avoid each other, leading to significantly fewer conflicts.
- Near-perfect case completion rates (CR ≈ 1000) across almost all configurations confirm that the GNN policy reliably guides robots to their goals; conflicts are the primary remaining bottleneck.

## Hardware Integration

The `IR_sensor/` directory contains C-language driver code and a Makefile for interfacing with infrared sensors on physical robot platforms. This allows the same learned policy to be applied in real-world settings by mapping sensor readings to the grid observation format expected by the model.
